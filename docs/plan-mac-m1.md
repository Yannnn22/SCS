# 算力受限版复现方案（单机 Mac M1）

> 本文档替代原计划里所有基于「RTX 4060 / Windows / 双机协作」的假设。
> 原计划见 [`plan.md`](plan.md)（保留作对照，但其第三、四节的日程已作废）。

---

## 0. 一句话说明改了什么

原计划建立在一个**不存在的硬件条件**上：RTX 4060 Laptop 8GB 显存。

实际环境：**Apple M1 / 16GB 统一内存 / 无 CUDA / macOS 15.1.1**。

这不是"换个机器跑"那么简单，它改变了三件事：

| 变化 | 原计划 | 现在 | 影响 |
|---|---|---|---|
| 加速后端 | CUDA（NVIDIA） | **MPS** | 代码要后端无关，不能写死 `cuda` |
| 显存模型 | 8GB **专用**显存 | 16GB **统一内存**（系统与模型共享） | 可用预算反而更紧：要扣掉系统占用 |
| 量化能力 | bitsandbytes 可用 | **不可用**（CUDA-only） | **QLoRA 这条路彻底消失** |
| 协作模式 | 双机 + 双分支 git | **单机单分支** | 删掉 `win/main`、删掉 Windows 提示词 |
| 执行者 | Windows 上的 agent | **用户本人**（见第 3 节） | 我写代码，你跑命令 |

## 1. 硬约束清单（规划的事实基础）

### 1.1 硬件与系统

```
芯片      Apple M1（8 核 CPU / 8 核 GPU / 16 核 NPU）
内存      16 GB 统一内存  ← 不是显存，是整机共享
macOS     15.1.1
磁盘      可用 103 GB
Python    /opt/homebrew/bin/python3.13 (3.13.2) 已建 .venv
```

### 1.2 ★ `bitsandbytes` 装不了 ⇒ QLoRA 不存在

这是本次改计划最重要的一条。

`bitsandbytes` 的 4bit/8bit 量化内核只针对 **CUDA** 实现，在 Apple Silicon 上
**无法安装**（官方也没有计划支持 MPS）。而 QLoRA 的定义就是
「4bit 量化的基座 + LoRA 适配器」——**没有量化就没有 QLoRA**。

**所以能做的只有 LoRA（非量化）**：基座以 fp16/bf16 加载，只训练低秩适配器。

这件事必须写进面试材料，因为它是个真实的、有技术含量的取舍结论：

> 「原方案用 QLoRA 是为了把 14B 塞进 8G 显存。换到 M1 后 bitsandbytes 不可用，
> 我做不了量化；于是一步退到 LoRA + 1.5B 模型——**代价是模型规模，收益是流程完全一致**。
> 而且我实测对比了量化前后的显存/速度差异……」

### 1.3 统一内存的真实预算

16GB 统一内存不是"16GB 可给模型用"。粗略账：

| 项 | 占用 |
|---|---|
| macOS 系统 + 常驻进程 | 3–5 GB |
| 浏览器 / 编辑器 / DSH 本身 | 1–3 GB |
| **可用于模型的余量** | **约 6–9 GB** |

按 fp16（每 10 亿参数约 2GB）估算单模型加载：

| 模型 | fp16 权重 | 训练时（含激活+优化器） | 结论 |
|---|---|---|---|
| Qwen2.5-0.5B | ~1.0 GB | ~3–4 GB | ✅ 稳妥，验证流程用 |
| Qwen2.5-1.5B | ~3.1 GB | ~6–8 GB | ⚠️ 主线目标，需实测 |
| Qwen3-1.7B | ~3.5 GB | ~7–9 GB | ⚠️ 边界 |
| Qwen2.5-3B | ~6.2 GB | ~11 GB+ | ❌ 基本不可行 |
| Qwen3-4B | ~8.0 GB | — | ❌ 仅推理都紧张 |

**⚠️ 上表是估算，不是实测。** 唯一实测锚点来自 Windows 那次：
Qwen2.5-0.5B 4bit 单步训练峰值 1.29 GB。**非量化会显著更高。**

**规划原则：所有"装得下吗"的结论必须由 `check_finetune_stack.py` 实测，不许按公式推断。**

### 1.4 LLM 推理：用现成的 Ollama，别自己扛

本机**已装 `ollama`**（`/usr/local/bin/ollama`）和 **LM Studio**（`lms`）。
这解决了最大的一块算力问题：

- **不要**在 Python 里加载 4B 级模型做推理——它会吃掉 8GB+ 统一内存
- **要**用 `ollama serve` 起服务，脚本走 OpenAI 兼容协议调用
- 这样推理进程与训练进程**不会同时抢内存**，且模型由 Ollama 管量化

推荐：`qwen3:4b`（约 2.5GB，质量与占用平衡）或 `qwen2.5:3b`。
`configs/base.yaml` 的 `llm.provider: openai_compatible` + `base_url: http://127.0.0.1:11434/v1`
本来就是为这个场景设计的，**不用改代码**。

## 2. 调整后的模块优先级

原计划 16 个阶段（P0–P16）是围绕「RAG + Agent + QLoRA」三条腿设计的。
单机 M1 的资源下，必须排优先级——**不是所有东西都值得做**。

### 第一优先级：RAG 全链路 + 真实指标（不可砍）

这是整个项目的**技术内核**，也是面试最容易被追问的部分。而且它对算力的需求最低：

| 环节 | 算力需求 | M1 可行性 |
|---|---|---|
| 语料整理 + 切分 | 无 | ✅ |
| BM25 | 无 | ✅ |
| BGE-M3 embedding（300–500 chunk） | 1.5–2GB | ✅ 走 MPS，分钟级 |
| Milvus Lite / FAISS 检索 | 极小 | ✅ |
| RRF 融合 | 无 | ✅ |
| Reranker（Cross-Encoder） | 2–3GB | ✅ 走 MPS，与 embedding **串行**加载 |
| 评测指标 | 无 | ✅ |
| **消融实验对照表** | 无 | ✅ **这是核心交付物** |

**产出**：L0→L4 每层的 HitRate/Recall/MRR/nDCG + 延迟，全部实测。

### 第二优先级：Agent 闭环 + NL2SQL（保留，但缩小）

| 环节 | 说明 |
|---|---|
| LangGraph 状态机 | ✅ 纯逻辑，无算力需求 |
| 意图分类 | ⚠️ 用小模型或规则+LLM，**不要**为分类单独加载一个模型 |
| NL2SQL 五层 | ✅ 主要是字符串处理 + sqlglot，LLM 调用走 Ollama |
| SQLite 业务库 | ✅ 纯数据 |
| 工具白名单 / 超时 / 重试 | ✅ 纯逻辑 |

**注意**：LLM 调用通过 Ollama，所以**每调一次都有秒级延迟**。
消融实验里要如实记录这个延迟——它是真实成本，不是缺点。

### 第三优先级：分层记忆 + 滑动窗口压缩（保留，降级实现）

- 短期记忆：进程内 dict（**不用 Redis**——本机没装，且单机场景没必要）
- 长期记忆：Milvus Lite collection，BGE-M3 向量
- 压缩：纯字符串/向量相似度逻辑，无算力需求

### 第四优先级：微调（缩水，但保留方法论）

| 项 | 原计划 | 现计划 |
|---|---|---|
| 量化 | QLoRA 4bit | ❌ 不可行 |
| 方法 | LoRA | ✅ LoRA（非量化 fp16） |
| 基座 | Qwen3-4B | **Qwen2.5-0.5B 先跑通 → 试 1.5B** |
| 数据量 | 1500–3000 条 | 300–800 条（够验证方法论） |
| 评测 | 格式/意图/SQL 可执行率 | 同样三维度，但样本量小 |

**明确不做的事**（写进面试材料，比硬凑更有说服力）：
- ❌ QLoRA / 任何量化微调（bitsandbytes 不可用）
- ❌ 14B 及以上模型的任何操作
- ❌ 真正的「效果提升」——0.5B 模型 SFT 后不会有质变，只验证**流程**与**格式合规率**
- ❌ 高并发 / 灰度发布 / 监控看板（单机无意义）
- ❌ 双机协作 / ACP / MCP 跨机（已放弃）

## 3. 协作模式：我写，你跑

**我（沙箱）的写入权限：**

```
会话工作区 /Users/Zhuanz/untitled folder/   ✅ 可写
/tmp                                        ✅ 可写
$HOME 其他目录                               ❌ 不可写
/opt/anaconda3/envs                         ❌ 不可写（系统权限）
```

**所以我不能**：装 Python 包到全局、建 conda 环境、下载大模型、跑训练。
**所以我能**：写所有代码、写文档、跑纯标准库的验证、用内置小样例自检逻辑。

**分工：**

| 谁 | 做什么 |
|---|---|
| 我 | 写/改所有源码与文档；每个模块自带 `if __name__` 自检块；设计实验与验收标准 |
| 你 | 在终端跑我给的命令；把**实际输出**贴回来；跑长任务（下载、训练） |

**每个模块的交付节奏**：我写 → 你跑自检 → 贴输出 → 我据实修 → 再跑。
**禁止我声称"应该能跑"**，验收一律以你的实际输出为准。

### 环境现状（需你确认一次）

```bash
# 我在工作区建了 .venv（Python 3.13.2），但装 torch 失败（沙箱限制）
# 请你在终端执行：
cd "/Users/Zhuanz/untitled folder/ec-agent-rebuild"
.venv/bin/python -m pip install torch --index-url https://download.pytorch.org/whl/cpu
.venv/bin/python -c "import torch; print(torch.__version__, torch.backends.mps.is_available())"
```

> 注意：Apple Silicon 的 MPS 支持**就在标准 macOS wheel 里**，
> 不需要 `--index-url` 也自带。上面加 `cpu` 通道只是为了确保拿到 CPU/MPS 版
> （而不是误装成 CUDA 版）。如果它报找不到，直接 `pip install torch` 即可。

## 6. 必须写进面试材料的「取舍与结论」

这套受限环境反而给了几个真实、有技术含量的结论。**别浪费它们**：

1. **QLoRA 为什么在 Mac 上做不了** —— bitsandbytes 的量化内核是 CUDA-only。
   这解释了一个常见困惑："为什么教程都用 CUDA"。
2. **统一内存 vs 专用显存** —— 16GB 统一内存 ≠ 16GB 显存。
   系统和其他进程要分走一部分，可用预算反而更紧。
3. **RAG 对算力的需求远低于微调** —— 我的 RAG 全链路在 M1 上跑得很轻松，
   而微调连 1.5B 都要精打细算。**这个对比本身就是有价值的工程判断**。
4. **L0→L4 消融的真实数字** —— 我会用实测证明原文档那些提升幅度是否站得住。
5. **原文档 6 处技术硬伤 + 我实测推翻的 3 处自己的预设**
   （16G 显存、Milvus 在 Windows 不可用、HF 可直连）。

## 7. 风险与止损

| 风险 | 止损 |
|---|---|
| torch/MPS 装不上 | 退 CPU 后端，RAG 全链路仍可跑（只是慢） |
| 1.5B 训练 OOM | 回退 0.5B 并如实记录规模上限 |
| BGE-M3 在 MPS 上不稳 | embedding 走 CPU（300–500 chunk 分钟级） |
| Ollama 模型下载慢 | 换更小模型，或先用规则/模板代替 LLM 调用打通链路 |
| 内存被其他进程占满 | 训练/评测前先关浏览器；用 `vm_stat` 看可用内存 |
| 时间不足 | **死保第 1 周**（RAG + 真指标），微调降为纯文档 |

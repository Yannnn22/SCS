# 微调实验报告：电商客服 LoRA（Qwen2.5-1.5B on M1）

> 本文档记录一次**完整跑通**的 LoRA 微调实验，包含成功与失败。
> 操作步骤见 [`finetune-walkthrough.md`](finetune-walkthrough.md)。
> 原理说明见 [`learning-log.md`](learning-log.md) 日志 2 / 4。

---

## 1. 实验配置（全部实测，非估算）

| 项 | 值 | 说明 |
|---|---|---|
| 硬件 | Apple M1 / 16GB 统一内存 | 无 CUDA |
| 后端 | MPS（torch 2.14.1） | bitsandbytes 不可用 ⇒ **非量化 LoRA** |
| 基座 | Qwen/Qwen2.5-1.5B-Instruct | 1.5B 是 16GB 上的上限附近 |
| LoRA | r=8, alpha=16, dropout=0.05 | target=[q,k,v,o] |
| 可训练参数 | **2,179,072 / 1,545,893,376 = 0.141%** | 与公式推算一致（见日志 4） |
| 学习率 | 2e-4 | LoRA 常用区间的中间值 |
| 批大小 | batch=1 × grad_accum=16 ⇒ 等效 16 | 内存换时间 |
| max_seq_len | 512 | 实际最长样本 246 token，无截断 |
| epochs | 5（35 优化步） | 未触发早停 |
| 数据 | 98 train / 20 val / 26 test | 零重叠（按答案分组切分） |

## 2. 训练过程（实测曲线）

```
step  7 | ep 1.99 | train 2.5272 | val 2.3051 | lr 1.90e-04 | rss 6.28G | 101.6s
step 14 | ep 2.99 | train 2.2230 | val 2.0014 | lr 1.45e-04 | rss 6.28G | 210.0s
step 21 | ep 3.99 | train 1.9736 | val 1.7540 | lr 8.16e-05 | rss 6.28G | 317.4s
step 28 | ep 4.99 | train 1.7995 | val 1.6226 | lr 2.61e-05 | rss 6.28G | 434.6s
step 35 | ep 5.99 | train 1.7239 | val 1.5976 | lr 4.27e-07 | rss 6.28G | 586.7s

总耗时 597s（约 10 分钟）    best val_loss = 1.5976
```

**诊断：健康，未过拟合。**

| 信号 | 观察 | 判断 |
|---|---|---|
| train ↓ / val ↓ 同步 | 2.53→2.22 / 2.31→2.00 | ✅ 正常学习 |
| val 未回升 | 单调下降到 1.5976 | ✅ 5 轮不够过拟合 |
| RSS 稳定 | 全程 6.28 GB 不涨 | ✅ 无内存泄漏 |
| 未触发早停 | patience=2 从未满足 | ✅ 还在提升期 |

**结论：5 个 epoch 不是上限。** 数据量小时过拟合风险主要在
`train 继续降而 val 开始升`，本实验未出现。若数据扩到 500+，
建议把 epochs 提到 8–10 并观察 val 拐点。

---

## 3. ★ 内存代价（必须知道的真实数据）

```
训练期间： swap used = 13.9 GB / 15.4 GB
           Pages free = 82 MB（物理内存几乎耗尽）
```

**16GB 跑 1.5B LoRA 会把内存打满并大量换页。** 三个后果：

1. **训练变慢** —— 10 分钟里相当部分时间在做内存换页
2. **SSD 写入磨损** —— 这是真实成本，不是理论担忧
3. **机器基本没法做别的事**

**"能跑"≠"跑得舒服"。** 1.5B 贴着 16GB M1 的上限。要长期训练应上 32GB 或云 GPU。

对照：0.5B 训练峰值 RSS 仅 **2.37 GB**，余量充足。

## 4. 效果评估（同一测试集 26 条 / 同一套解码参数）

解码参数：`temperature=0`（贪心，保证可复现）、`top_p=0.9`、`max_new_tokens=200`。

| 指标 | 基线 | 微调后 | 变化 | 判定 |
|---|---|---|---|---|
| **关键词覆盖率** | 0.2940 | **0.4970** | **+69%** | ✅ 有效 |
| **分步骤率** | 0.1923 | **0.5000** | **+160%** | ✅ 有效 |
| 平均回答长度 | 97.2 | 93.1 | −4% | ➖ 基本不变 |
| 敬语使用率 | 0.5000 | 0.4231 | −15% | ⚠️ 退步 |
| **JSON 格式合规率** | 0.0000 | **0.0000** | 0 | ❌ **失败** |

（注：覆盖率指标修过一次，见第 5 节。）

### 4.1 ✅ 成功的部分

**分步骤率 +160%** 是最清晰的收益。对照实例：

```
用户: 我怀疑我的号被盗了怎么办？

[基线] 您好！如果您怀疑您的账号被他人盗用，可以按照以下步骤进行处理：
       1. **立即登录账户**：首先尝试直接登录到您的账户，看是否能正常访问。
       2. **检查账户信息**：仔细核对账户中的个人信息和交易记录...
       （加粗标题、解释性文字、结构松散）

[微调] 您好，遇到账号被冒用的情况，可以按照以下步骤处理：
       1. 立即冻结或停用该账号。
       2. 通过官方渠道（如平台客服）申请临时冻结或永久封禁。
       3. 提交警方报案，提供相关证据。
       4. 联系银行更改支付密码和绑定银行卡...
       （纯编号清单、无 markdown 加粗、与训练风格一致）
```

**模型学到了训练数据的呈现风格**：纯编号清单、不用 `**加粗**`、
一条一句、不给多余解释。这正是 LoRA 该做的事。

### 4.2 ❌ 失败的部分：JSON schema 未被学会

**现象**：13 条 JSON 样本，微调前后合规率**都是 0**。

```
参考: {"scene": "service", "need_tool": false, "tool": null, "urgency": "low"}
预测: {"intent": "query", "sub-intent": "refund"}          ← 完全不同的字段
```

**诊断过程**：

1. 先查训练数据 —— **schema 完全正确**（13 条 JSON 样本字段无误）→ 排除数据 bug
2. 再查失败模式分布：

| 失败原因 | 基线 | 微调后 |
|---|---|---|
| `not-json`（压根不是 JSON） | 5 条 | **0 条** |
| `missing:...`（是 JSON 但字段错） | 8 条 | **13 条** |

→ **模型学会了"输出 JSON 格式"这件事，但没学会"用我的字段名"。**

**根因分析**（这条比结论重要）：

```
JSON 训练样本仅 13 条（占 train 的 13%）
而 schema 是"任意自定义的"，没有任何先验可借
预训练里对 {"intent": ...} 这类字段有很强的先验
→ 13 个反例不足以覆盖预训练先验
```

**这是微调的经典失败模式：要改变的行为离预训练先验越远，需要的数据越多。**
"输出 JSON" 靠近先验（学得快），"用我指定的四个字段名" 远离先验（学得慢）。

**修法**（按性价比排序）：
1. **扩 JSON 样本到 150–200 条**（最直接，成本为零——写代码生成）
2. 提高 JSON 样本在训练集中的占比（现在 13%，可提到 30%）
3. 加大 LoRA rank（8→16）以增强拟合能力
4. 增加 epochs（现未过拟合，还有空间）

### 4.3 ⚠️ 意外的退步：编造了具体平台名

```
用户: 你能直接把我的钱退到我微信吗？

[微调] 您好，目前我们无法直接将退款金额退还至您的微信账户...
       - 1. 登录「京东」APP；      ← ★ 京东！我的训练数据里根本没有京东
       - 2. 点击右下角「我的」；
       - 3. 找到「已发货」查看订单详情；
```

**微调后的模型编造了一个具体的平台名称。**

这**恰好印证了** learning-log 日志 2 的核心结论：

> **LoRA 微调改的是「怎么说」，不改「知道什么」。**
> 模型学到了我的风格（编号步骤），但内容上的幻觉一点没少——
> 反而因为学会了"更具体地列步骤"，它变得更敢于编造具体细节。

**这是本次实验最有教学价值的发现**：微调可能**放大**幻觉的表现形式。
业务知识必须靠 RAG 提供，并在 Prompt 里约束"只依据参考资料回答"。

## 5. 指标本身也修过一次（评估的元问题）

**第一版覆盖率指标**：把参考答案里「4 字以上连续中文」当关键词，要求逐字匹配。

```
参考: "拒收后包裹会退回商家...运费可能由您承担"
预测: "可以的，您可以直接拒收商品...联系快递公司确认..."
得分: 0.3     ← 明明答对了要点
基线平均: 0.069   ← 明显失真
```

**问题**：逐字匹配对中文太苛刻——换同义词、调语序、加修饰词都会失配。

**修正后**用两层：

| 层 | 内容 | 权重 | 理由 |
|---|---|---|---|
| 硬信息 | 数字、时效、专有名词 | 0.6 | 说错了是实质错误，严格匹配合理 |
| 内容重合 | 字符级重合率 | 0.4 | 对改写宽容，衡量"大致说了什么" |

修正后基线从 0.069 → 0.294，且能正确识别"答对但措辞不同"的情况。

**教训**：**指标失真比模型差更危险**——它会让你误判优化方向。
评估脚本写完后，一定要人工看几条原始输出验证指标是否合理。

## 6. 结论与下一步

### 做成了什么

| 项 | 结果 |
|---|---|
| 完整微调流程 | ✅ M1 上 10 分钟跑通，含 loss masking、梯度累积、早停 |
| 风格迁移 | ✅ 分步骤率 +160%，学会训练集的呈现方式 |
| 数据工程 | ✅ 零泄漏切分、长度可分析、可复现 |
| 诚实的评估体系 | ✅ 三维度分开、先建基线、同条件对照、指标自检 |

### 做不成什么（写进面试材料）

| 项 | 原因 |
|---|---|
| QLoRA / 4bit 量化 | bitsandbytes 是 CUDA-only，Apple Silicon 不可用 |
| JSON schema 习得 | 13 条样本不足以覆盖预训练先验；**数据量问题不是代码问题** |
| 消除幻觉 | 微调不改知识；**反而可能放大幻觉的具体性** |
| 舒适的训练环境 | 16GB 打满 + 13.9GB swap，能跑但不舒服 |

### 下一步（按优先级）

1. **扩 JSON 样本到 150–200 条**，重跑，验证 schema 合规率能否从 0 起来
   —— 这是最有价值的单点改进
2. 扩 QA 样本到 500+（当前 98 条），观察过拟合拐点
3. 对比 r=8 vs r=16，看容量是否是瓶颈
4. 把 RAG 接上，验证"微调管风格 + RAG 管知识"的分工是否成立

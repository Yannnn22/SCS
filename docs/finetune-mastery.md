# 模型微调实操全解：认识、参数、与面试题

> 本文档配合一次真实实验写成（Qwen2.5-1.5B LoRA on M1，见 [`finetune-report.md`](finetune-report.md)）。
> 所有数字都是实测值，不是教科书举例。**面试里能说出具体数字的人，比能背定义的人值钱得多。**

# 第一部分：先建立正确的认识

## 1.1 ★ 最重要的一条：微调不是首选，是最后一招

**面试高频陷阱题：**"我们有个业务需求，你会怎么让模型支持？"

**错误回答**："收集数据做微调。"

**正确思路是按成本从低到高逐级尝试：**

| 手段 | 成本 | 适合解决 | 不适合解决 |
|---|---|---|---|
| **1. Prompt 工程** | 最低，改几个字 | 输出格式、角色口吻、简单约束 | 知识不足、复杂推理 |
| **2. RAG（检索增强）** | 中，要建知识库 | **知识类问题**（业务规则、产品信息） | 风格、格式 |
| **3. 微调（SFT）** | 高，要数据和算力 | **稳定的格式/风格/领域术语** | **知识、事实准确性** |
| **4. 继续预训练** | 最高 | 全新领域的语料分布 | 大多数业务场景 |

**为什么这个顺序不能颠倒？**

```
改 Prompt  →  5 分钟，0 成本，立刻验证
建 RAG     →  几天，但知识更新只需改文档，不用重训
做微调     →  几周，而且知识变了要重新训（灾难性）
```

**微调最被滥用的场景**：把 FAQ 塞进训练集"让模型学会业务知识"。
这必然失败，原因见 1.3。

**我在实验里验证了这条**：微调后模型输出「登录京东 APP」，
而训练数据里根本没有京东——**微调没有给它任何新知识，只给了它新的说话方式**。

---

## 1.2 微调到底改变了什么

模型内部的权重矩阵 `W`（比如 896×896）代表它学到的映射关系。

```
全量微调：  W → W + ΔW        ΔW 与原权重同尺寸（896×896）
LoRA 微调： W → W + B·A       A是 8×896，B是 896×8，B·A 秩最高为 8
```

**LoRA 的核心假设**：微调所需的权重变化 `ΔW` 是**低秩**的
（即它可以被少数几个方向近似表达）。

**为什么这个假设成立？** 因为微调只是在原有能力上做**小幅调整**
（改风格、学格式），不需要重建整个权重空间。
如果任务是"从零学一门新语言"，低秩假设就不够用了——那时要全量微调。

**参数量对比**（实测数据）：

```
Qwen2.5-1.5B 全参数量         1,545,893,376
LoRA(r=8, q/k/v/o) 可训练量       2,179,072   ← 0.141%
```

**省下了 99.86% 的训练量**，而实验证明它仍然能学到风格迁移。

## 1.3 ★★ 微调的三个真实边界（面试必考）

### 边界 1：微调改不了知识

```
[微调前] 很抱歉，我们无法直接将您的退款金额退还至您个人的微信账户中...
[微调后] 您好，目前我们无法直接将退款金额退还至您的微信账户...
         - 1. 登录「京东」APP；          ← ★ 我的数据里没有京东
         - 2. 点击右下角「我的」；
```

**这次实验最值钱的发现**：微调后模型的幻觉**没有减少，反而更具体了**。
因为它学会了"给编号步骤"这个模式，于是更敢于填充具体细节。

**深层原因**：SFT 的损失函数是"预测下一个 token"。
模型学到的是**在什么语境下该说什么类型的话**，
而不是**某个事实是否真实**。后者需要知识注入（RAG）或事实性对齐（RLHF/DPO）。

### 边界 2：微调改不了推理能力

SFT 不会让 0.5B 模型学会 14B 的推理水平。
**它优化的是"输出分布"，不是"思考能力"。**
想让小模型做复杂推理，靠的是 CoT 提示、工具调用、或换更大的模型。

### 边界 3：微调会"灾难性遗忘"

如果训练数据全是电商客服，模型可能**丢失通用对话能力**，
变得连"今天天气怎么样"都答不好。

**缓解手段**：
- 混合一定比例的通用数据（比如 10–20%）
- 只训 LoRA 而非全量（LoRA 天然更保守，因为原权重冻结）
- 保持学习率不要过大、epochs 不要过多

**为什么 LoRA 天然缓解遗忘**：原权重 `W` 完全冻结不动，
模型只是在外挂了一个小修正项。想"忘掉"原有能力，必须先把它覆盖掉——
而低秩修正项的容量有限，很难彻底覆盖。

## 1.4 微调方法的谱系（要说得出区别）

| 方法 | 基座权重 | 可训参数 | 内存需求 | 适用 |
|---|---|---|---|---|
| **全量微调** | fp16 全更新 | 100% | 极高（权重的 4–8 倍） | 数据极多、追求极致效果 |
| **Freeze（冻结）** | 冻结大部分层 | 10–30% | 中 | 已过时，不如 LoRA |
| **LoRA** | 冻结，旁路低秩 | 0.1–1% | 低 | **主流选择** |
| **QLoRA** | **4bit 量化** + 旁路 | 0.1–1% | **比 LoRA 再低 3–4 倍** | 显存极度受限 |
| **Adapter** | 冻结，插入小 MLP | 1–5% | 低 | 已被 LoRA 取代 |
| **Prefix/P-Tuning** | 冻结，学前缀向量 | <0.1% | 极低 | 效果不稳定 |

**面试常问：「LoRA 和 QLoRA 的区别是什么？」**

**标准答案分两层：**

1. **字面区别**：QLoRA = LoRA + 4bit 量化的基座。
   Q = Quantized。LoRA 的基座仍是 fp16/bf16。

2. **★ 关键洞察**（这层才是加分项）：
   **量化只影响"基座怎么存"，不影响"学什么"。**
   证据是我这次实验的实测数据：

   ```
   Windows 上 4bit QLoRA：可训练参数 1,081,344
   Mac 上非量化 LoRA：  可训练参数 1,081,344   ← 完全一致！
   ```

   **为什么一致**：LoRA 适配器的参数量 = `rank × (输入维度 + 输出维度) × 目标模块数`，
   这个公式里根本没有"基座精度"这一项。

3. **引申：QLoRA 的三项省内存技术**（说出来很加分）

   | 技术 | 作用 |
   |---|---|
   | **NF4 量化** | 4bit NormalFloat，针对正态分布权重设计，比普通 int4 精度高 |
   | **Double Quantization** | 对量化常数本身再量化，每个参数再省约 0.4 bit |
   | **Paged Optimizer** | 优化器状态在显存不足时换到内存，避免 OOM 峰值 |

# 第二部分：实操流程与关键决策

## 2.1 完整流程（八个阶段）

```
① 明确目标   → 你要改的是"格式/风格"还是"知识"？后者别用微调
② 选基座     → 模型规模 × 是否 Instruct × 量化能力
③ 造数据     → 占 70% 工作量，最容易出错
④ 验证链路   → 用小模型跑通，别拿大模型试错
⑤ 建基线     → 训之前先测！否则无法证明微调有效
⑥ 训练       → 盯 loss 曲线、内存、是否早停
⑦ 评估       → 三维度分开报，同条件对照
⑧ 迭代       → 看 badcase 决定是扩数据还是调参数
```

**★ 阶段 ④ 和 ⑤ 是最常被跳过的两步，也是我这次实验里最省事的安排：**

```bash
# ④ 用小模型验证链路（1GB，几分钟）
python scripts/check_finetune_stack.py --model Qwen/Qwen2.5-0.5B-Instruct

# ⑤ 训之前先测基线（这一步决定了你的"提升"是否可信）
python src/finetune/eval_sft.py --model Qwen/Qwen2.5-1.5B-Instruct --tag baseline
```

**为什么 ④ 不能省**：直接用 1.5B 试错，每次版本不兼容要重下 3GB 模型。
用 0.5B 几分钟就能确认「torch + transformers + peft + 设备后端」四件套兼容。

**为什么 ⑤ 不能省**：没有基线，你的"提升 20%"可能只是评测方式变了。
**基线是唯一能证明微调有用的东西。**

## 2.2 ★★ 数据工程：微调成败的 70%

### （1）数据格式

| 格式 | 结构 | 适用 |
|---|---|---|
| **Alpaca** | `{instruction, input, output}` | 单轮指令，最通用 |
| **ShareGPT** | `{conversations: [{from, value}]}` | 多轮对话 |
| 纯文本 | `{text}` | 继续预训练 |

**Alpaca 三字段的 loss 语义**（对应实际做法）：

| 字段 | 作用 | 是否计算 loss |
|---|---|---|
| `instruction` | 系统提示 | ❌ |
| `input` | 用户输入 | ❌ |
| `output` | 期望输出 | ✅ **只算这个** |

### （2）★ Loss Masking：实现细节与常见错误

**朴素做法的问题**（把整段拼起来算 loss）：

```
"你是客服助手。用户问：能退货吗？答：可以，条件..."
 └────── 也在算 loss ──────┘└── 也在算 ──┘
```

两个后果，第二个更隐蔽：
1. 模型被迫学"预测用户会问什么"——无用
2. **answer 的 loss 被 prompt token 稀释**。若 answer 只占 20% token，
   那么 loss 里只有 20% 在指导"怎么答"

**正确实现**（本次实验采用）：

```python
# 整段 tokenize，然后定位 assistant 回复头，把之前的 label 置 -100
full_ids  = tokenizer(full_text)["input_ids"]
prompt_ids = tokenizer(prompt_text)["input_ids"]   # 到 assistant 头为止

labels = list(full_ids)
for i in range(len(prompt_ids)):
    labels[i] = -100        # PyTorch 会忽略这些位置
```

**为什么不用"分别 tokenize 再拼接"**：

```
tokenizer(A + B)  ≠  tokenizer(A) + tokenizer(B)
```

BPE 在拼接边界处的合并行为不同，会错位几个 token。
**这种错位不会报错，只会让 mask 边界偏掉——是隐蔽 bug。**

**★ 必做的自检**（我在训练脚本里加了）：

```python
assert ex["n_answer"] > 0, "answer 全被 mask 掉了，loss 会恒为 0"
```

如果一条样本的 prompt 太长、把 answer 挤出窗口，
那条样本的 label 会**全是 -100**，loss 恒为 0，**等于白训**。
必须统计有多少这种样本。我这次实验实测：`超过 max_seq_len 的样本 0 条`，
最长样本 246 token（窗口 512），余量充足。

### （3）★★ 数据划分：答案泄漏（本次踩了三次）

**这是我认为最有教学价值的一段。**

**尝试 1：按业务分组分层抽样**

```python
key = f"{s['group']}|{s['topic']}"     # 按主题分组
```

结果：`train∩test=3`，**答案泄漏**。

根因：同一 topic 下，一条答案配了多个问法（"衣服能退吗" / "买错了咋整"）。
变体被拆散到不同集合后，**测试集里出现训练集见过的答案**。
指标会虚高，**而且从数字上完全看不出来**。

**尝试 2：按 topic 整体切分**

泄漏修好了，但：`val=6 条, test=3 条`。**测试集太小，测出来的分数没有统计意义。**

**尝试 3（最终）：按【答案】分组** ★

```python
def leak_key(s): return str(hash(s['output']))   # 按答案内容分组
```

结果：`train∩test=0`，`val=20`，`test=26`。

**关键认识（值得背下来）**：

> **泄漏的根源是「不同集合共享同一答案」，不是「共享同一主题」。
> 所以分组键应该是答案，不是主题。**

**★ 而且我的"重叠检查"本身也写错过一次：**

```
错误版：比较 input（问句）集合  →  报 train∩test=14（假警报）
```

因为按答案分组时，同一答案的不同问法**合法地**分布在多个集合。
**问句重复 ≠ 泄漏。**

**正确判据：一条完整 `(input, output)` 不得跨集合。**

**这段经历在面试里极有说服力**——它证明你不仅会写代码，
还能**识别出"看起来对但其实错"的检查逻辑**。

### （4）数据量与质量

**经验值**（不是铁律，但可以当起点）：

| 目标 | 数据量 |
|---|---|
| 验证流程跑通 | 50–100 条 |
| 学格式/风格 | **200–500 条** |
| 稳定领域适配 | 1000–5000 条 |
| 改变模型行为范式 | 1 万条以上 |

**★ 我这次实验证明了一条更重要的规律**：

```
QA 样本 85 条 → 风格迁移成功（分步骤率 +160%）
JSON 样本 13 条 → schema 学习完全失败（合规率 0 → 0）
```

**结论：所需数据量取决于「目标任务离预训练先验有多远」。**

- "输出 JSON" 靠近先验 → 学得快
- "用我指定的四个字段名" 远离先验 → 13 条不够压制先验

**这个洞察比任何"多少条够用"的经验值都有用**，因为它能解释失败。

### （5）数据质量的红线

| 问题 | 后果 | 检查方法 |
|---|---|---|
| **训练/测试重叠** | 指标虚高 | 按 `(input,output)` 查重 |
| **答案过于简短** | 模型学会答空话 | 统计 answer 长度分布 |
| **格式不统一** | 模型输出混乱 | 抽样人工看 |
| **含事实错误** | 模型学会错误 | 人工抽查 10% |
| **用同一个模型生成数据又训它** | 放大它的缺点 | 用更强的模型生成 |

**★ 我踩过"答案过于简短"这个坑**：

第一版用 `lines[0]`（第一行）做"简洁版答案"。但多行答案的第一行往往只是开场白：

```
完整: "您好，平台支持价格保护。\n条件：签收后15天内降价...\n流程：..."
简洁: "您好，平台支持价格保护。"     ← 条件和流程全丢了
```

结果：答案最短只有 **12 字**，模型会学到"遇问题答一句空话"。
改为"逐行取要点但不丢行"后，最短 73 字、p50 110 字。

**教训：数据增强手段必须检查它的副作用。** "造更多变体"听起来是好事，
但如果变体质量差，等于往训练集里掺噪声。

## 2.3 ★★ 显存/内存优化（面试必问"显存不够怎么办"）

**按性价比排序的五种手段：**

| 手段 | 省多少 | 代价 | 优先级 |
|---|---|---|---|
| **1. 梯度累积** | 与 accum 倍数成正比 | 训练变慢 | ⭐⭐⭐ 必用 |
| **2. 梯度检查点** | 激活内存降到 O(1) | 慢 20–30% | ⭐⭐⭐ 必用 |
| **3. 降低 max_seq_len** | 注意力是 O(n²)，效果显著 | 长样本被截断 | ⭐⭐ 慎用 |
| **4. 4bit 量化（QLoRA）** | 权重降 4 倍 | 需 bitsandbytes | ⭐⭐⭐ 但 Mac 不可用 |
| **5. LoRA 减小 rank** | 优化器状态线性下降 | 拟合能力下降 | ⭐ 最后手段 |

### ★ 梯度累积的正确实现（最常见的错误）

**原理**：用 N 次小 batch 前向，累加梯度，再更新一次参数。
数学上等价于 batch_size = N，但内存只需 1 个样本的。

```python
loss = model(**batch).loss / grad_accum    # ★ 必须除以 accum 步数！
loss.backward()
if (step + 1) % grad_accum == 0:
    optimizer.step()
    optimizer.zero_grad()
```

**为什么必须除以 `grad_accum`？**

```
不除：16 次梯度累加 → 梯度值放大 16 倍 → 等效学习率变成 16×lr
除：  梯度均值        → 与真实大 batch 等价
```

**这是一个非常隐蔽的错误**：loss 曲线看起来"下降得很快"，
你会以为训练顺利，实际上是学习率被悄悄放大了 16 倍，
可能导致**后期震荡或发散**。

### ★ 梯度检查点的正确用法

```python
model.gradient_checkpointing_enable()      # 开启
model.enable_input_require_grads()         # ★ 必须配套！
```

**为什么需要第二行？**

开启检查点后，前向不保存中间激活，反向时重算。
但**重算需要输入张量有梯度信息**。如果输入（embedding 输出）被标为不需要梯度，
反向时梯度传不回底层，表现是 **loss 完全不降**。

**这个 bug 很隐蔽**：代码不报错、loss 也有值（就是不动），
很多人会误以为是学习率太小或数据有问题。

### 其他内存手段

| 手段 | 说明 |
|---|---|
| `optimizer.zero_grad(set_to_none=True)` | 比置 0 更省内存 |
| 混合精度（fp16/bf16） | 激活内存减半；MPS 上 fp16 比 bf16 稳 |
| 及时 `del` 中间变量 + `torch.mps.empty_cache()` | 释放缓存 |
| 减少 LoRA 的 target_modules | 优化器状态是参数量的 2 倍（AdamW 的 m 和 v） |

**★ 实测内存数据（本次实验）**：

```
Qwen2.5-0.5B 训练       峰值 RSS 2.37 GB
Qwen2.5-1.5B 训练       峰值 RSS 6.28 GB（全程稳定不涨）
训练期间 swap used      13.9 GB / 15.4 GB   ← ★ 物理内存被打满
```

**注意最后一行**：能跑通 ≠ 跑得舒服。
16GB 跑 1.5B 会大量换页，**慢且伤 SSD**。

# 第三部分：关键参数逐个讲

## 3.1 LoRA 结构参数

| 参数 | 本次取值 | 含义 | 怎么调 | 调错会怎样 |
|---|---|---|---|---|
| `r`（rank） | 8 | 低秩矩阵的秩，**参数量与它成正比** | 简单任务 4–8；复杂 16–64 | 太小欠拟合；太大过拟合且省不下内存 |
| `lora_alpha` | 16 | 缩放系数，**有效缩放 = alpha/r** | 经验 `alpha = 2r` | 与 r 脱节会导致有效学习率偏离预期 |
| `lora_dropout` | 0.05 | 适配器上的 dropout | 小数据 0.05–0.1；大数据 0 | 小数据上设 0 会过拟合 |
| `target_modules` | q,k,v,o | 给哪些层挂适配器 | 只挂注意力最省；加 MLP 效果更好 | 挂太多参数翻倍、显存吃紧 |

### ★ 关于 `r` 和 `alpha` 的常见困惑

**问题**：为什么不直接用学习率控制强度，要两个参数？

**答案**：因为 LoRA 的更新形式是 `ΔW = (alpha/r) · B·A`。
`alpha/r` 这个缩放**与学习率解耦**，带来一个实用好处：

```
想把 r 从 8 改成 16（增加容量），同时保持有效更新幅度不变：
  r=8,  alpha=16  → alpha/r = 2
  r=16, alpha=32  → alpha/r = 2   ← 只调 alpha，不用重新搜学习率
```

**做消融实验时这个性质很重要**——改 r 不用重新调 lr。

### ★ 参数量怎么算（本次实验验证过公式）

```
可训练参数 = Σ_over_target_modules [ r × (输入维度 + 输出维度) ] × 层数
```

**实测验证（两个不同结构的模型都对上）**：

| 模型 | d_model | 层数 | heads/kv_heads | kv_dim | 每层 | 总计 | 实测 |
|---|---|---|---|---|---|---|---|
| Qwen2.5-0.5B | 896 | 24 | 14 / 2 | 128 | 45,056 | 1,081,344 | ✅ 一致 |
| Qwen2.5-1.5B | 1536 | 28 | 12 / 2 | 256 | 77,824 | 2,179,072 | ✅ 一致 |

**★ 关键陷阱：不能假设所有投影都是方阵。**

Qwen2.5 用 **GQA（分组查询注意力）**：14 个 query 头但只有 2 个 kv 头。

```
q 投影: 896 → 896     k 投影: 896 → 128   ← kv 维度只有 128，不是 896！
v 投影: 128 → 896     o 投影: 896 → 896

考虑 GQA:  每层 45,056  →  总计 1,081,344  ✅
忽略 GQA:  每层 57,344  →  总计 1,376,256  ❌ 差 27%
```

**GQA 为什么存在**：推理时 KV cache 是显存瓶颈。
标准 MHA 要存所有头的 KV，GQA 只存 2 个头 → **KV cache 省 7 倍**，质量损失很小。

---

## 3.2 优化相关参数

| 参数 | 本次取值 | 含义 | 怎么调 |
|---|---|---|---|
| `lr` | 2e-4 | 学习率 | **LoRA 常用 1e-4 ~ 3e-4**（见下） |
| 优化器 | AdamW | 标准选择 | 一般不改 |
| `weight_decay` | 0.0 | L2 正则 | LoRA 上通常设 0 |
| `warmup_ratio` | 0.05 | 前 5% 步数线性升温 | 小数据 0.03–0.1 |
| `max_grad_norm` | 1.0 | 梯度裁剪阈值 | 防梯度爆炸 |

### ★ 为什么 LoRA 的学习率比全参微调大 10–100 倍

```
全量微调：直接更新 15 亿个已有权重
          这些权重已训练好，大改动会破坏 → 步长必须极小（1e-5 量级）

LoRA：    只更新 200 万个【新增】小矩阵，且初始为 0
          从零开始学，需要更大步长才能快速收敛 → 常用 2e-4
```

**面试如果被问"你的学习率为什么是 2e-4"，答这一条就够了。**

### ★ Warmup 为什么必要

训练初期参数随机（LoRA 是 A/B 都从初始化开始），梯度方向噪声大。
直接用大学习率会震荡甚至发散。前若干步线性升温，让模型"站稳"再加速。

本次实测：`总优化步数 35，warmup 1 步`。
**35 步太少，warmup 只有 1 步——这在小数据集上是正常的**，
但也说明 warmup 在几百条数据时作用有限。

## 3.3 批大小与序列长度

| 参数 | 本次取值 | 作用 | 权衡 |
|---|---|---|---|
| `batch_size` | 1 | 单次前向的样本数 | 显存第一杀手 |
| `grad_accum` | 16 | 累积多少步更新一次 | 内存换时间 |
| `max_seq_len` | 512 | 单条最大 token 数 | 注意力 O(n²)，显存第二杀手 |

**等效批大小 = batch_size × grad_accum = 1 × 16 = 16**

**为什么不用 batch_size=16 直接跑？**

```
batch_size=16 → 16 条样本的激活同时驻留内存 → OOM
bs=1, ga=16   → 每次只放 1 条，梯度累加，16 次后更新
              → 数学等价，内存只需 1 条的
```

**代价：慢 16 倍**（16 次前向才更新一次参数）。

**关于 `max_seq_len` 的选择**：
- 必须覆盖你的最长样本，否则 answer 被截断（见 loss masking 那节）
- 本次实验：最长样本 246 token，设 512，**余量 2 倍**，安全
- **设太大会浪费显存**（注意力 O(n²)），设太小会截断

## 3.4 训练轮数与早停

| 参数 | 本次取值 | 说明 |
|---|---|---|
| `epochs` | 5 | 最多跑几轮 |
| `eval_steps` | 7 | 每多少步验证一次 |
| `patience` | 2 | val_loss 连续几次不降就停 |

**本次实测曲线**：

```
step  7 | ep 1.99 | train 2.5272 | val 2.3051
step 14 | ep 2.99 | train 2.2230 | val 2.0014
step 21 | ep 3.99 | train 1.9736 | val 1.7540
step 28 | ep 4.99 | train 1.7995 | val 1.6226
step 35 | ep 5.99 | train 1.7239 | val 1.5976   ← 未过拟合
```

**判断：还在提升期，5 轮不是上限。** 若数据扩到 500+，建议提到 8–10 轮观察拐点。

# 第四部分：训练过程怎么读（诊断能力）

## 4.1 ★ loss 曲线的四种形态与对策

| 形态 | 诊断 | 对策 |
|---|---|---|
| train ↓, val ↓ | ✅ 健康 | 继续，直到 val 走平 |
| train ↓↓, val ↓ 后 ↑ | ❌ **过拟合** | 早停 / 减 r / 加 dropout / **加数据** |
| train 几乎不动 | ❌ **lr 太小 或 loss masking 错了** | 先查 mask（answer 是否被误 mask），再调 lr |
| train 震荡 / NaN | ❌ **lr 太大 或精度溢出** | 降 lr；MPS 上用 fp32 试 |

**★ "train 不动"最常见的原因不是 lr，而是 loss masking 写错。**
必须**先打印一条样本的 labels**，确认非 -100 的比例 > 0，再去调 lr。

## 4.2 必须监控的指标

| 指标 | 为什么 | 危险信号 |
|---|---|---|
| train_loss | 学习情况 | 不降 / NaN |
| **val_loss** | **泛化能力** | 回升 = 过拟合 |
| **学习率** | 确认调度生效 | 与预期不符 |
| **进程 RSS** | 统一内存机器上判断真实占用 | 持续上涨 = 泄漏 |
| 每步耗时 | 判断是否异常 | 突然变慢 = 在换页 |
| 梯度范数 | 诊断是否爆炸/消失 | 远大于 1 或接近 0 |

**★ MPS 上没有 `max_memory_allocated()`**，只有 `current_allocated_memory()`（瞬时值）。
统一内存机器上应该看**进程 RSS**（`resource.getrusage().ru_maxrss`），
因为它包含 Python 堆、库、以及未归还的缓存。

# 第五部分：评估（最容易糊弄自己的一环）

## 5.1 ★★ 四条铁律

1. **同一份测试集**
2. **同一套 Prompt 模板**
3. **同一套解码参数**（temperature / top_p / max_tokens）
4. **只换模型**

**任何一条不一致，对照就失效。**

**★ 我本次实验的做法**：`temperature=0`（贪心解码）。
**为什么评测要用贪心**：随机采样会让两次评估结果不同，无法复现。
生成式任务上线才需要多样性，评测需要可复现性。

## 5.2 ★ 为什么必须先建基线

没基线 = 无法证明微调有效。

**很多人的"提升"其实是**：
- 评测方式变了（换了个更宽松的指标）
- Prompt 写法变了
- 测试集变了

**只有「同条件、只换模型」的对照才是证据。**

## 5.3 指标设计：本次踩的坑

**第一版覆盖率指标**：把参考答案里「4 字以上连续中文」当关键词，逐字匹配。

```
参考: "拒收后包裹会退回商家...运费可能由您承担"
预测: "可以的，您可以直接拒收商品...联系快递公司确认..."
得分: 0.3      ← 明明答对了要点
基线平均: 0.069  ← 明显失真
```

**问题**：逐字匹配对中文太苛刻，换同义词、调语序、加修饰都会失配。

**修正后两层设计**：

| 层 | 内容 | 权重 | 理由 |
|---|---|---|---|
| 硬信息 | 数字、时效、专有名词 | 0.6 | 说错是实质错误，严格合理 |
| 内容重合 | 字符级重合率 | 0.4 | 对改写宽容 |

修正后基线 0.069 → 0.294，能正确识别"答对但措辞不同"。

**★ 教训：指标失真比模型差更危险——它会让你误判优化方向。**
评估脚本写完后，**必须人工看几条原始输出**验证指标是否合理。

## 5.4 分维度报告，不要合成一个"准确率"

| 维度 | 判定方式 | 本次结果 |
|---|---|---|
| 格式合规率 | 程序化（JSON 解析） | 0 → 0 ❌ |
| 内容覆盖率 | 程序化（关键词） | 0.294 → 0.497 ✅ |
| 结构化程度 | 程序化（分步骤检测） | 0.192 → 0.500 ✅ |
| 表述得体性 | **人工抽样** | 需人工看 |

**为什么不能合成**：混在一起的"准确率"掩盖了"哪个维度有效、哪个无效"。

# 第六部分：面试题（按真实套路组织）

## 6.1 「你会不会做微调」类

**Q1：什么情况下你会选择微调，而不是 RAG / Prompt 工程？**

> 按成本从低到高试。**知识类问题用 RAG**（更新只需改文档，不用重训）；
> **格式/风格/领域术语用微调**；Prompt 能解决的不上微调。
>
> 我在实验里验证过微调的边界：微调后模型输出了「登录京东 APP」，
> 而我的训练数据里根本没有京东——**微调给的是说话方式，不是知识**。
> 所以业务规则必须走 RAG。

**Q2：LoRA 和 QLoRA 的区别？**

> 字面上 QLoRA = LoRA + 4bit 量化的基座。但关键洞察是
> **量化只影响基座怎么存，不影响学什么**。
>
> 实测证据：同一个 LoRA 配置，4bit QLoRA 和非量化 LoRA 的
> 可训练参数量完全一致（1,081,344）。因为参数量 =
> `rank × (输入维度 + 输出维度) × 目标模块数`，公式里没有"基座精度"这一项。
>
> QLoRA 省内存靠三项技术：NF4 量化、Double Quantization、Paged Optimizer。

**Q3：LoRA 的 r 和 alpha 是什么？为什么需要两个参数？**

> `r` 是低秩矩阵的秩，决定可训练参数量（参数量 ∝ r）。
> `alpha` 是缩放系数，有效缩放 = `alpha/r`。
>
> 需要两个参数是因为这个缩放**与学习率解耦**：
> 想把 r 从 8 改到 16 增加容量时，只要同步把 alpha 从 16 改到 32，
> 有效更新幅度就保持不变，**不用重新搜学习率**。做消融实验时很有用。
>
> 经验值 `alpha = 2r`，我用的就是 r=8 / alpha=16。

## 6.2 「数据怎么做」类

**Q4：微调数据要多少条？**

> 取决于**任务离预训练先验有多远**，不是固定数字。
>
> 我实验里有个对照：QA 样本 85 条就成功学到了风格（分步骤率 +160%），
> 但 JSON schema 样本 13 条完全失败（合规率 0 → 0）。
> 因为"输出 JSON"靠近先验，"用我指定的四个字段名"远离先验——
> **13 条反例压不过预训练里对 `{"intent": ...}` 的强先验**。
>
> 所以经验值（格式/风格 200–500 条，领域适配 1000+）只是起点，
> 真正的判据是：**目标行为离先验越远，需要的数据越多。**

**Q5：你怎么保证测试集是干净的？**

> 核心是防**答案泄漏**。我踩了三次：
>
> 1. 按业务分组分层抽样 → `train∩test=3`，因为同一答案配了多个问法，
>    变体被拆散后测试集出现训练答案
> 2. 改成按主题整体切 → 泄漏修好了，但 val 只剩 6 条，**测试集太小没统计意义**
> 3. 最终**按答案内容分组** → 0 泄漏 + val=20/test=26
>
> 关键认识：**泄漏的根源是"不同集合共享同一答案"，不是"共享同一主题"。**
> 所以分组键应该是答案。
>
> 还有一点：我的**重叠检查本身也写错过**——第一版比较问句集合，
> 报了 `train∩test=14` 的假警报。因为按答案分组时问句合法地分布在多个集合。
> **正确判据是一条完整 (input, output) 不得跨集合。**

**Q6：数据质量怎么保证？**

> 我踩过一个具体的坑：做数据增强时，用 `lines[0]`（第一行）生成"简洁版答案"。
> 但多行答案的第一行往往只是开场白：
> `"您好，平台支持价格保护。"` —— 条件和流程全丢了。
> 结果答案最短只有 12 字，**模型会学到"遇问题答一句空话"**。
> 改成"逐行取要点但不丢行"后最短 73 字。
>
> **教训：数据增强手段必须检查副作用**，"造更多变体"如果质量差就是掺噪声。
>
> 其他红线：训练/测试查重、抽样人工看 10%、
> **不要用同一个模型生成数据又训它**（会放大它的缺点）。

## 6.3 「资源不够怎么办」类

**Q7：显存不够怎么优化？**

> 按性价比排序：
> 1. **梯度累积**（必用）—— bs=1 配 grad_accum=16，数学上等价 batch=16
>    但内存只需 1 条。代价是慢 16 倍。
> 2. **梯度检查点**（必用）—— 激活内存从 O(层数) 降到 O(1)，
>    代价是慢 20–30%。
> 3. 降 max_seq_len —— 注意力是 O(n²)，效果显著，但会截断长样本
> 4. 4bit 量化（QLoRA）—— 权重降 4 倍
> 5. 减 LoRA rank —— 优化器状态是参数量的 2 倍（AdamW 的 m/v），最后手段
>
> ⚠️ 两个实现细节容易错：
> - **梯度累积时 loss 必须除以 accum 步数**，否则等效学习率被放大 N 倍
> - **`gradient_checkpointing_enable()` 必须配 `enable_input_require_grads()`**，
>   否则梯度传不回底层，表现是 loss 完全不降（很隐蔽）

**Q8：你怎么知道模型过拟合了？**

> 看 **val_loss 相对 train_loss 的走势**，不是看 train 本身。
>
> - train ↓ 且 val ↓ → 健康
> - train 继续 ↓ 但 **val 开始 ↑** → 过拟合，该早停
>
> 我这次 5 轮跑完 train 2.53→1.72、val 2.31→1.60，
> **两者同步下降、val 未回升**，说明还没到过拟合点。
>
> 缓解手段：早停、减 r、加 dropout、**加数据**（最有效）。

## 6.4 「怎么评估」类

**Q9：怎么证明微调有效？**

> 四条铁律：同一测试集、同一 Prompt 模板、同一解码参数、**只换模型**。
> 而且**必须先建基线**——训之前测一次，训后再测一次。
>
> 我用的解码参数是 `temperature=0`（贪心），因为评测要可复现；
> 随机采样会让两次结果不同。
>
> 结果分维度报，不合成一个"准确率"：
> - 分步骤率 0.192 → 0.500（+160%）✅
> - 关键词覆盖率 0.294 → 0.497（+69%）✅
> - JSON 格式合规率 0 → 0 ❌
>
> **分开报才能看出"哪个维度有效、哪个无效"。**

**Q10：如果微调后效果反而变差怎么办？**

> 先分清是**评估问题**还是**模型问题**。
>
> 我做这个实验时，第一版覆盖率指标用「4 字以上连续中文逐字匹配」，
> 基线只有 0.069——**明显是指标失真，不是模型差**。
> 修正为「硬信息 0.6 + 字符级重合 0.4」后基线 0.294。
>
> **指标失真比模型差更危险，因为它会让你误判优化方向。**
> 评估脚本写完必须人工看几条原始输出验证。
>
> 确认是模型问题后，按这个顺序查：
> 数据（质量/量/格式）→ loss masking → 学习率 → r 容量 → epochs。

## 6.5 「边界与坑」类

**Q11：微调能消除幻觉吗？**

> **不能，而且可能放大。**
>
> 这是我认为最有价值的实测发现：微调后模型输出
> `- 1. 登录「京东」APP；`，而我的训练数据里根本没有京东。
> 幻觉没减少，**反而更具体了**——因为它学会了"给编号步骤"这个模式，
> 更敢于填充具体细节。
>
> 原因：SFT 的损失是"预测下一个 token"，
> 模型学的是**在什么语境下说什么类型的话**，而不是**事实是否真实**。
> 事实性要靠 RAG（提供真材料）+ Prompt 约束（只依据材料回答）。

**Q12：微调会导致灾难性遗忘吗？怎么缓解？**

> 会。如果训练数据全是电商客服，模型可能丢失通用对话能力。
>
> 缓解手段：
> 1. 混合 10–20% 通用数据
> 2. **只训 LoRA 而非全量**——原权重冻结，只外挂小修正项，
>    低秩修正的容量有限，很难彻底覆盖原有能力
> 3. 控制学习率和 epochs
>
> 这也是 LoRA 相对全量微调的一个隐性优势。

**Q13：你怎么知道该用多大的模型？**

> 先算**内存预算**，再看**任务需求**。
>
> 内存这块要分清两种硬件：
> - **独显**：看专用显存。8GB 只能 LoRA 微调 4B（QLoRA）
> - **统一内存（Apple Silicon）**：不是"显存"，CPU/GPU 共享整机内存。
>   16GB 里要扣掉系统 3–5GB 和其他进程 1–3GB，**实际可用 6–9GB**
>
> 我实测：Qwen2.5-0.5B 训练峰值 RSS 2.37GB，1.5B 是 6.28GB。
> **但 1.5B 训练时 swap 用了 13.9GB/15.4GB**——能跑通，但会大量换页，
> **慢且伤 SSD**。所以"能跑"和"跑得舒服"是两回事。
>
> 任务需求方面：先问"我要改的是格式还是知识"。改格式，小模型够用；
> 要提升推理能力，微调解决不了，得换更大的模型。

## 6.6 反问面试官的问题（加分项）

- 「这个任务的目标是改**格式/风格**，还是补**知识**？」——问清边界
- 「现有数据量多少？标注质量怎么控制的？」
- 「推理侧的延迟和成本预算是多少？」——决定模型规模上限
- 「怎么定义"效果好"？有基线吗？」

**这些问题体现的是工程判断力，不是技术点背诵。**

  max_seq_length: 512     # 必须 >= 最长样本
  warmup_ratio: 0.05
  max_grad_norm: 1.0
  lr_scheduler: cosine

  fp16: true              # MPS 上比 bf16 稳

data:
  format: alpaca
  loss_masking: true      # ★ 只对 answer 算 loss
  split: "8:1:1"
  min_samples: 200        # 风格类任务的起点

## 五个最容易犯的错

| # | 错误 | 后果 | 检查 |
|---|---|---|---|
| 1 | 不做 loss masking | 模型学复述问题 | 打印 labels，确认非 -100 比例 |
| 2 | 梯度累积不除 accum | 等效 lr 被放大 N 倍 | loss = loss / grad_accum |
| 3 | 忘了 `enable_input_require_grads` | loss 完全不降 | 与 checkpointing 成对出现 |
| 4 | 测试集答案泄漏 | 指标虚高且看不出 | 按 (input, output) 查重 |
| 5 | 不建基线 | 无法证明有效 | 训之前先测 |

## 一句话总结每个要点

- **微调是最后一招**，先试 Prompt 和 RAG
- **微调改怎么说，不改知道什么**
- **数据决定上限**，占 70% 工作量
- **loss masking 是必做**，不是优化项
- **数据量取决于离先验多远**，不是固定数字
- **先建基线**，否则提升不可信
- **指标会骗人**，必须人工验证
- **能跑 ≠ 跑得舒服**，swap 是真实代价
